# Аудит: панель поверх штатного XKeen

Дата: 2026-10-02. Исследованный исходник панели: `8adff1e00e89515b37aac1d7d6e7e1df924a9143` (beta.5). Это аудит и предложение изменения архитектуры, не отчёт о готовой переработке или успешно установленном VPN.

Контракт дальнейшей работы: [Issue #121](https://github.com/popiposter/xkeen-control/issues/121).

## Вывод

Требование пользователя и реализованная архитектура разошлись. Нужна графическая оболочка над штатным XKeen. Сейчас значительная часть панели реализует собственный appliance manager: устанавливает компоненты, заменяет lifecycle и interception, задаёт обязательный набор конфигураций, распознаёт ограниченное число прежних установок и самостоятельно восстанавливает их транзакции. Это основной источник сложности. Исправлять по одному очередные `layout-*` недостаточно.

Рекомендация: сохранить Go/React панель, защиту доступа, подписки, механизм проверки конфигурации, шифрованный экспорт и полезные части наблюдения/выбора узла. Вернуть XKeen владение его установкой, обновлениями, зависимостями, запуском, cron и сетевыми хуками. Собственный updater оставить только у панели. Не переписывать проект целиком.

## Граница и метод проверки

- После запроса остановки никаких подключений к роутеру, установок, перезапусков или сетевых замеров через VPN не выполнялось. Пользователь переустанавливает opkg самостоятельно.
- Выполнены три прохода: карта владельцев и upstream-команд; проверка вызываемых путей и отказов; контрпримеры к заявлениям об установке и качестве. Независимый второй рецензент в этом аудите не привлекался; он включён в план как отдельный gate.
- Проверены `AGENTS.md`, `SECURITY.md`, архитектура/roadmap, контракты Setup, конфигурации, уведомлений и текущие issues #1/#4/#81. Изучены production-код затронутых подсистем и соответствующие тестовые швы. Это глубокий аудит перечисленных контрактов, не заявление о прочтении каждой строки и отсутствии всех дефектов.
- Upstream прочитан без исполнения: `jameszeroX/XKeen` commit `5aaece27a70d5bd002c615248614914ebbc4569d` от 2026-10-01, официальный stable asset 2.0 и beta-архив в этом commit. Секреты и приватные конфигурации в аудит не включены.
- Два локальных Go overlay-probe вызвали существующие функции панели без изменения production-кода: сериализация реального каталога Setup и фактическая формула adaptive score. Данные публичные/синтетические.
- Sanitized evidence: [journal](evidence/xkeen-foundation-v1/journal-proof.json), [score](evidence/xkeen-foundation-v1/score-proof.json), [upstream assets](evidence/xkeen-foundation-v1/upstream-asset-comparison.json), [объём кода](evidence/xkeen-foundation-v1/size-metrics.json), [команды и границы проверок](evidence/xkeen-foundation-v1/verification.txt).

## Что действительно предоставляет XKeen

На дату аудита GitHub branches API возвращает только `main`. `install.sh --beta` использует `main/test/xkeen.tar.gz`. Внутренние обозначения Dev/Beta ещё встречаются, но выбирать несуществующую ветку `dev` как текущую точку установки нельзя.

| Проверенный объект | Факт |
|---|---|
| Stable 2.0 | 73 082 байта; SHA256 `dfcc0ccbd30e343ee17a0308596793d4e12ae50c5129953071621208a273f937`; 71 файл; `-sbt` и модулей speed balancer в архиве нет |
| Beta из main `5aaece2` | 125 747 байт; SHA256 `1d246871d8fc9df2e68e80cef18562e6222661e40eaea1b6853cf8e0e6348b5f`; 72 файла; speed balancer присутствует |
| Каталог панели | Принимает старый закреплённый beta build `51725f5…`, архив 111 435 байт, а не текущий upstream beta |

Отказ от штатного speed balancer устраняет **одну** причину выбирать beta. Это не доказывает пригодность stable: в beta есть и другие изменения policy routing, режимов перехвата, совместимости и диагностики. Сначала нужен сравнительный чистый install/upgrade contract-test stable и beta. Для текущего проектирования исходная совместимость — проверенный beta; stable станет предпочтительным только при прохождении того же набора требований.

Штатный install делает проверку Entware, ставит недостающие зависимости, предлагает proxy core, загружает компоненты и geodata, формирует конфиги/регистрацию/автозапуск и расписания. `--beta` выбирает канал bootstrap, но **не превращает весь последующий `xkeen -i` в стабильный неинтерактивный API**. Например, выбор core, geodata, версии и cron может требовать ввода.

Команды `-uk`, `-ux`, `-ug`, `-ugc/-dgc`, `-start/-stop/-restart`, `-kb/-xb` уже существуют. При этом штатный cron сейчас прежде всего обновляет geodata через `xkeen -ug`; нельзя обещать штатное автоматическое обновление всех компонентов. `update_cron_geofile_task` удаляет прежние cron-вызовы `-ugi/-ugs/-ux/-uk`. Полная инвентаризация диспетчера приложена в [матрице команд](xkeen-command-inventory-v1.md).

Источники: [upstream architecture](https://github.com/jameszeroX/XKeen/blob/5aaece27a70d5bd002c615248614914ebbc4569d/docs/architecture.md), [dispatcher](https://github.com/jameszeroX/XKeen/blob/5aaece27a70d5bd002c615248614914ebbc4569d/scripts/xkeen), [installer](https://github.com/jameszeroX/XKeen/blob/5aaece27a70d5bd002c615248614914ebbc4569d/install.sh), [cron registration](https://github.com/jameszeroX/XKeen/blob/5aaece27a70d5bd002c615248614914ebbc4569d/scripts/_xkeen/02_install/07_install_register/03_register_cron.sh).

## Подписки и узлы: сохранить основу

Полезны существующие `nodes.Registry`, стабильные identity, refresh reconciliation, сохранение ручного enable/disable, batch Apply, полная проверка candidate Xray, bounded fetch и защита от загрузки из приватной сети. `ParseSubscriptionBody:174` импортирует VLESS/REALITY из raw/base64, другие протоколы игнорирует. WL-правило для новых узлов уже есть; сохранённый ручной выбор не должен сбрасываться на каждом refresh.

Ограничения следует показывать точно: это не универсальный импорт всех форматов. Невалидный поддерживаемый профиль по-прежнему отклоняет snapshot. Пользователь просил не засорять UI сообщениями о пропущенных неподдерживаемых протоколах — это сохраняется. Поле новой ссылки остаётся видимым обычным input; сохранённые URL не должны автоматически появляться в статусах/логах. Возможность изменить ссылку не требует возвращать секрет во все GET.

Основной рефакторинг здесь — подключить Apply к штатному lifecycle XKeen и сохранению соседних конфигурационных областей. Не переписывать parser/registry ради новой архитектуры. Provider content нужен только для операторских тестов, никогда для публичных fixtures.

## Выбор узла: сравнение и решение

| Свойство | Native XKeen beta SB | Текущий panel adaptive |
|---|---|---|
| Выбор | Максимальная measured download speed + hysteresis | RTT, download, upload, guardrail, dwell |
| Объём | Последовательно все узлы; нет сопоставимого общего generation budget в `sb_tick` | ≤6 кандидатов, ≤144 MiB/180 s, раз в 3 часа по умолчанию |
| Живость | Tick скорости не заменяет отдельную быструю проверку | 1 KiB/60 s, порог 2 отказа, validate before switch |
| Изменение runtime | Xray override | Тот же override |
| Ограничения | Нет полного quality/failure model; сбой всех замеров оставляет прежний override | Calibration, exploration, startup delay и смерть владельца override требуют исправления |

Максимальный payload panel adaptive при восьми полных циклах в сутки — **1 152 MiB/сутки**, без ручных диагностик и протокольных накладных расходов. «Bounded» не означает «малый для любого тарифного плана»; нужен показ бюджета и экономичный режим.

Оставить три явно взаимоисключающих режима: native Xray, native XKeen SB, panel adaptive. По умолчанию при первом подключении панели не переключать владельца. Рекомендуемый конечный режим panel adaptive можно сделать default только после сравнительного replay/аппаратного gate. В нём штатный SB выключается его собственной командой; это единственное оправданное исключение из принципа «XKeen работает штатно». Два override writer одновременно запрещены.

## Предлагаемое разделение ответственности

| Область | Владелец и роль панели |
|---|---|
| Install, prerequisites, ядра, geodata, native backup, service, hooks, policies, native cron | XKeen. Панель обнаруживает capabilities, вызывает закрытые операции и проверяет результат. Не содержит копию shell-реализации. |
| Config routing/DNS/XKeen | Native файлы — исполняемая конфигурация. Панель читает их, сохраняет неизвестные части и атомарно меняет только заявленные поля/свои области. Отдельный обязательный полный appliance twin больше не нужен. |
| VPN секреты/подписки | Существующий nodes registry остаётся единственной panel authority; генератор меняет только управляемые outbounds. Для ручных внешних edits есть import/reconcile с diff. |
| Выбор узла | Один выбранный владелец. Panel adaptive — дополнительный модуль, не условие запуска XKeen. |
| Update панели | Нынешний подписанный panel updater с проверкой источника и rollback. |
| Portable backup, GUI geodata, bot | Дополнительные удобства панели поверх проверенных адаптеров. |

Native команды не образуют готовый RPC. Нужен узкий adapter: фиксированный executable и аргументы, typed inputs, serial operation receipt, защищённый bounded вывод и независимая проверка конечного состояния. Там, где команда интерактивна, сначала добавить/согласовать machine-readable режим upstream либо протестировать строго версионный диалог. Нельзя подменять это произвольным shell API или `yes | xkeen ...`. Отсутствие пригодного способа вызова должно блокировать конкретное действие, не создавать ещё один установщик.

## Geodata и понятный routing

Предлагаемый UX: «Категории» → файл/источник/версия → доступные категории и количество записей → просмотр/поиск → действие VPN/DIRECT/BLOCK. Отдельно «Мои списки» для доменов/IP и «Почему адрес идёт так?» для объяснения порядка правил.

Поиск показывает **что именно хранится**: полный домен, доменный суффикс, keyword, regex, IP/CIDR и атрибут категории. Список доменов нельзя выдавать за полный список всех разрешаемых ими IP. Принадлежность категории и итог first-match routing — разные ответы. Для IP lookup нужны longest-prefix/membership данные; для domain lookup — тип match и нормализация IDNA. Меняются geodata hashes — обновляются index и валидность Preview.

Индекс строится лениво, без распаковки всех баз в огромный JSON на flash. Ограниченные страницы/ответы, отмена поиска, измеренный RSS на ARM64. При неизвестном формате доступен status файла, а не повреждение policy. Native обновление баз инициирует проверку реально используемых категорий.

## Backup и Telegram

Перенос: экспортировать поддержанные native настройки, custom lists, managed nodes/subscriptions, routing policy, selection preferences и описание требуемых geodata источников/категорий. На новом роутере сначала работает штатный XKeen, затем Restore показывает mapping интерфейсов/политик и diff. Не переносить исполняемые файлы, PID/locks, transient statistics, сетевые правила, listener/private management address и auth. Telegram credentials — только отдельная явная опция зашифрованного переноса.

Telegram: первым этапом полезные alerts + status/restart/switch через те же typed operations. Для одного token должен существовать один receiver; каждый роутер с одним общим token не должен сам потреблять `getUpdates`. Простой первый вариант — отдельный bot на роутер. Единый bot для нескольких роутеров — отдельный optional controller с outbound authenticated связью роутеров; это сознательная новая стоимость, не скрытая обязательная cloud-зависимость. При отсутствии такой инфраструктуры single-bot multi-router не объявляется готовым. [Официальный Bot API](https://core.telegram.org/bots/api#getupdates).

## Как менять и проверять

1. Сначала вертикальный результат на чистом Entware: штатный install XKeen → работающий сервис → панель рядом → импорт подписки → проверенный LAN-трафик. Никакого исходящего релиза только ради очередного `layout-*` патча.
2. Затем native update/cron и конфигурационные editor adapters; после этого удалить заменённые component writers, сохранив только необходимое чтение исторических recovery records.
3. Затем сравнительно квалифицировать выбор узла и резервирование, построить geodata browser/routing explanation, расширить portable backup и Telegram.
4. Приёмка обязана включать реальные upstream артефакты и Keenetic-семантику. Моки POSIX/Linux не заменяют kernel modules, NDM, USB `/opt`, native cron и трафик с LAN-клиента.

Подробные задачи, зависимости, критерии и ограничения: [план переработки](architecture-xkeen-foundation-v1.md). Чистый роутер пользователя пока не используется: аудит сам по себе не возобновляет установку.
