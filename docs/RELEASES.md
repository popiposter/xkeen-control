# Releases, bootstrap and panel updates

Issue #2 adds the implementation for public signed releases, a bounded first-install bootstrap and panel-only self-update. This Draft PR does not make a stable release available and does not advertise the one-command installer as production-ready.

## Release authority

Only a GitHub Release is an install/update source. Raw branches, branch archives, Actions artifacts and arbitrary URLs are not accepted. The supported artifact is `linux/arm64` and every release contains the binary, init script, fixed updater helper, installer, deterministic manifest, Ed25519 manifest signature and `SHA256SUMS`.

The manifest signs exact public metadata, source commit, source epoch, artifact sizes/hashes and compatibility flags. The installer verifies internal consistency before first installation. An installed binary uses the pinned public-key path for normal checks and updates; release/API hosts, redirects, body sizes and channels are bounded.

The production public key is intentionally not configured in this implementation branch. Synthetic keys exist only in Go fixtures. The protected GitHub `release` environment and production signing key pair are an operator gate; no stable release may be published until they are provisioned and the published assets are downloaded and independently re-verified.

## Bootstrap boundary

`scripts/install.sh` requires root, `/opt`, Entware `opkg`, `linux/arm64` and bounded free space. It installs only explicitly missing prerequisites, never performs a blanket package upgrade, never changes node/Xray/XKeen/policy state and never automates the upstream interactive component installer. Missing XKeen/Xray/configuration is a healthy Setup Mode state.

The first panel password is generated by the Go binary with `crypto/rand`, stored only as a bcrypt hash under root-only permissions and printed once to the invoking terminal. A rerun preserves the existing credential/listener/state. Authenticated password replacement clears the setup marker and invalidates sessions.

## Panel update boundary

The typed update API uses fixed release policy (`manual`, `notify`, or `auto-stable`), authenticated session + origin + CSRF checks, `/tmp/xkeen-control/panel-update` candidates and one persistent previous panel generation. The external helper has only `install` and `rollback` operations and fixed panel paths. It cannot execute arbitrary commands or modify Xray, XKeen, routing, DNS, Observatory or the node registry. Update and rollback acquire the existing C.1 lifecycle coordinator.

## Qualification sequence

Use the focused fixture `bash scripts/test-release.sh` (or its Docker equivalent), then the documented full command:

```powershell
pwsh -NoProfile -File scripts/dev-check.ps1
```

Production release and Keenetic panel-only upgrade/rollback/re-apply qualification are post-merge gates. This implementation PR performs no production-router mutation.
